# AGENTS.md — bringing an LLM up to speed on BirdDog PLAY Patcher

Orientation for an AI assistant (or a new human) picking this project up cold. `CLAUDE.md`
holds the short command reference; this file explains the model and the traps.

---

## 1. What this is

A static web page that assembles a BirdDog PLAY firmware **package** in the browser and hands
it to you as a `.fw` download. Vanilla JS, no framework, no build step, no npm dependencies.

The one insight the whole design rests on: **a valid package needs neither the user's firmware
file nor any vendor key.** The stock updater does `tar xf` then runs `./update` as root with no
signature check, so a package is just a gzip'd tar with an executable `update` at the top level.
That means no upload, no decryption, no secret — and therefore no server-side work.

If you find yourself adding a step that decrypts the vendor's `bdpff` payload, stop. See §6.

## 2. Layout

```
public/
  fw.js          THE ENGINE. ustar writer + reader, gzip, SHA-256, tailscale extraction.
                 No DOM, no network — that is what lets test/ exercise the real module.
  app.js         UI, fetch, progress log. Imports fw.js.
  index.html     the page, including the operational warnings
  assets/        GENERATED by scripts/build-assets.sh. Gitignored. Do not edit.
src/worker.js    static assets + the pkgs.tailscale.com proxy. The only server code.
installer/       what runs as root on the device. `update` is the installer proper.
agent/           bdkvm — Go source for the NDI KVM endpoint, plus a prebuilt arm64 binary
test/            builds a package in Node using public/fw.js
scripts/         build-assets.sh (assemble), sync-from-re.sh (pull from upstream research repo)
```

## 3. Where the truth lives

The installer and the agent are **developed in a separate private research repo**
(`birddog-re`), which holds the static analysis explaining why any of this works. This repo
carries a downstream copy so it can build and deploy alone.

`scripts/sync-from-re.sh` pulls that copy forward and **exits 1 if anything changed**. Editing
`installer/` or `agent/*.go` here will be silently overwritten on the next sync. Fix upstream.

Each file has exactly one committed copy in this repo: installer scripts in `installer/`, the
agent binary in `agent/dist/`. `public/assets/` is generated from both and is gitignored, so
there is no second copy to drift.

## 4. Traps

- **`CompressionStream('gzip')` is not reproducible across engines.** Chrome and Node configure
  zlib differently, so the same tar produces different `.fw` bytes. When comparing a
  browser-built package against a Node-built one, compare the **uncompressed tar** digest. A
  fixed mtime in `fw.js` makes the tar layer reproducible; nothing makes the gzip layer so.
- **ustar name fields are 100 bytes** and `tarHeader` throws rather than truncating. Any new
  payload path must stay short.
- **The installer must restart `BirdDogRunner`.** The vendor's `birddog-update-wrapper` stops it
  before calling `./update` and only ever restarts it by rebooting. An installer that exits
  without doing one or the other leaves the device with a dark HDMI output, looking bricked.
- **The camera payload is not offered by this web tool.** `installer/update` still carries a
  `WITH_CAM` block from upstream; it no-ops because the flag defaults to 0 *and* the block
  requires the directory to exist. The test asserts both guards — if you add the camera option,
  those assertions are what to update.
- **The KVM agent installs to `/userdata/bd-kvm`, not `/userdata/birddog-kvm`.** The vendor's own
  KVM hooks are a 1.0.34 feature, absent on 1.0.30, and the vendor updater does
  `rm -rf /userdata/birddog-kvm` on every update. The package *carries* the payload at
  `userdata/birddog-kvm/` — only the install destination differs. This looks like a bug twice.
- **`pkgs.tailscale.com` serves no `Access-Control-Allow-Origin`.** That is the entire reason a
  Worker exists. Keep the proxy narrow: hardcoded host, strict version pattern, two routes.

## 5. Verifying a change to the archive writer

Do not trust the page's own reader to validate its own writer. The checks worth repeating:

```bash
scripts/build-assets.sh && node test/build-package.mjs
tar tzvf test/out/BirdDog_PLAY-custom-citest.fw          # real tar must agree
python3 -c "import tarfile; tarfile.open('test/out/BirdDog_PLAY-custom-citest.fw').getmembers()"
```

Then extract and `cmp` the members against `installer/` — the test does this for `update`, and
it is the check that catches a subtly wrong header far better than a size comparison.

## 6. The line this project does not cross

The research this is built on recovered a static AES key that BirdDog uses across their whole
product line. **That key is not here, is not needed here, and must never be added here.** The
package format requires no decryption, which is precisely why this tool can be public while the
research repo is not.

Practically: no feature that reads, decrypts or repacks a vendor `.fw`. The test asserts that a
generated package contains no reference to the vendor payload; treat that assertion as a policy
check, not a formality.
