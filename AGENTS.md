# AGENTS.md — bringing an LLM up to speed on BirdDog PLAY Patcher

Orientation for an AI assistant (or a new human) picking this project up cold. `CLAUDE.md`
holds the short command reference; this file explains the model and the traps.

---

## 1. What this is

A static web page that assembles a BirdDog PLAY firmware **package** in the browser and hands
it to you as a `.fw` download. Vanilla JS, no framework, no build step, no npm dependencies.

The one insight the whole design rests on: **a valid package needs neither the user's firmware
file nor any vendor key.** The stock updater does `tar xf` then runs `./update` as root with no
signature check, so a package is just a gzip'd tar with an executable `update` at the top level.
That means no upload, no decryption, no secret — and therefore no server-side work.

If you find yourself adding a step that decrypts the vendor's `bdpff` payload, stop. See §6.

## 2. Layout

```
public/
  fw.js          THE ENGINE. ustar writer + reader (pax/GNU/prefix aware), gzip, SHA-256,
                 tailscale extraction, and readModule — the only gate a user's module passes.
                 No DOM, no network — that is what lets test/ exercise the real module.
                 PACKAGE/OPTIONS: every member a package carries, in pack order.
  app.js         UI, fetch, progress log. Imports fw.js and packs from PACKAGE.
  index.html     the page, including the operational warnings
  modules.html   the contract for third-party modules, written for their authors
  site.css       shared by both pages
  assets/        GENERATED by scripts/build-assets.sh. Gitignored. Do not edit.
src/worker.js    static assets + the pkgs.tailscale.com and MediaMTX release proxies. The
                 only server code. Pins the MediaMTX version the gateway is built against.
installer/       what runs as root on the device. `update` is the installer proper.
agent/           bdkvm — Go source for the NDI KVM endpoint, plus a prebuilt arm64 binary
player/          bdplay, the USB media player — Go source, the PDFium/exFAT helper build
                 scripts, and dist/ (the binaries the page serves; mutool never)
converter/       bdcam, the UVC converter — Go source and dist/
gateway/         bdgw, the streaming gateway panel — Go source and dist/
omt/             bdomt, the OMT receiver — Go source, the libvmx patch and build, and dist/
tailscale-ui/    bdts, the birdUI Tailscale panel — Go source and dist/
module-template/ a working third-party module; CI proves fw.js accepts it
test/            builds a package in Node using public/fw.js; modules.mjs reads archives
                 written by the SYSTEM tar; fixtures/module/ is the module the CI package carries
scripts/         build-assets.sh (assemble), sync-from-re.sh (pull from upstream research repo),
                 make-kit.sh + kit.mjs (the release kit)
kit/             what the release kit adds: NOTICE.md, licenses/, and README.md (the format)
```

## 3. Where the truth lives

The installer and the agent are **developed in a separate private research repo**
(`birddog-re`), which holds the static analysis explaining why any of this works. This repo
carries a downstream copy so it can build and deploy alone.

`scripts/sync-from-re.sh` pulls that copy forward and **exits 1 if anything changed**. Editing
`installer/` or `agent/*.go` here will be silently overwritten on the next sync. Fix upstream.

Each file has exactly one committed copy in this repo: installer scripts in `installer/`, the
agent binary in `agent/dist/`. `public/assets/` is generated from both and is gitignored, so
there is no second copy to drift.

The other on-device programs are **developed here**: `player/`, `converter/`, `gateway/` and
`tailscale-ui/` were their own public repos until 2026-10-11 and came in with their history
(`git subtree` merges, so `git subtree split --prefix=<dir>` recovers each). Each folder is
its own Go module with its own `go.mod`, `build.sh`, `AGENTS.md` and `docs/`; read that
folder's `AGENTS.md` before changing it. Its `build.sh` writes `<dir>/dist/<name>-linux-arm64`,
which is the committed binary build-assets.sh stages — so a source change ships only when
someone rebuilds, tests on a unit and commits that binary. CI vets, tests and compile-checks
the source; it never rebuilds the shipped binary. There is deliberately **no `go.work`**: it
would resolve one set of dependency versions across every module, so a folder's `build.sh`
would build against versions its own `go.sum` never named. birddog-re's `fwbuild` takes these
binaries from a patcher checkout's `<dir>/dist/`.

## 4. Third-party modules

A module is `modules/<name>/` in the package with a `module.conf` and an `install`; `update` runs
each `install` as root, from that directory, after the built-in payloads. The contract for
authors is `public/modules.html`; the reference implementation of an author's side is
`module-template/`, which CI builds and feeds to this checkout's `readModule`. Invariants:

- **`readModule` in fw.js is the only gate, and it is structural.** Archive shape, names, the
  100-byte path budget, links, ELF architecture, size. It does not and cannot judge what
  `install` does; the page says so in as many words. Do not add a check that pretends otherwise.
- **`RESERVED_MODULE_NAMES` must track the installer's own `/userdata/bd-*` paths and units.**
  A module named `cam` would install over bd-cam. The CLI builder in birddog-re carries the same
  list; change both.
- **The installer's guarantees are what make untrusted-by-us code safe to run:** subshell,
  `timeout`, exit logged and skipped, modules before the `BirdDogRunner` restore. The test
  asserts each of those against `installer/update`. Never weaken them for a convenience.
- **Flag and directory travel together** (`WITH_MODULES=1` and `modules/` present), the same
  guard pattern as every other payload. The test checks both directions.
- **Test the reader against real tar programs, never against fw.js's writer.** `test/modules.mjs`
  shells out to the system tar; CI's GNU tar is the only place the `././@LongLink` path is
  exercised by the real thing (a hand-built archive covers it on a Mac).
- Modes are normalised on the way in: `install`/`uninstall` 0755, anything with an exec bit
  0755, everything else 0644. A hand-built archive with no exec bits still installs.

## 5. Traps

- **MediaMTX is never an asset and never committed.** 62 MB unpacked is over the 25 MiB cap;
  the browser fetches the pinned release through the Worker and verifies GitHub's published
  SHA-256. The pin (`MEDIAMTX_VERSION` in `src/worker.js`) must match `MediaMTXVersion` in
  `gateway/render.go` (CI fails if not) and `MEDIAMTX_VERSION` in birddog-re's `build.sh`
  (private, so nothing checks it) — the gateway's rendered configuration is only validated
  against that one release.
- **Member paths live in `PACKAGE` in `fw.js`, not in `app.js`.** Burrow ports that table to
  pack from the release kit's `assets/`, so a path or mode typed into `app.js` would make the page
  and Burrow build different packages. Changing the table changes Burrow's packages too: tell the
  Burrow side. `test/kit.mjs` fails if `app.js` names a member path or asset of its own, packs out
  of table order, or if a package packed from the kit's `assets/` by the table isn't
  byte-identical to `test/build-package.mjs`'s. That test file keeps its own hand-written paths on
  purpose, as the independent copy; change both.
- **The kit's shape is Burrow's contract:** `kit.json`, `assets/` (public/assets/ as
  build-assets.sh writes it, minus `support-footer-version.js`) and `NOTICES/`. `kit.json` has
  exactly the keys in `kit/README.md`, every value read from `src/worker.js` or `fw.js`. Add a key
  or a file only with Burrow in step.
- **The kit never carries Tailscale, MediaMTX, mutool, a vendor `.fw` or a key.** `test/kit.mjs`
  checks the first three by name and the vendor payload by content. It carries the licence
  notices and source offer the page shows; `kit/licenses/pdfium/` is the licence directory of
  the exact pdfium-binaries release `player/dist/libpdfium.so` came from (chromium/7999), so
  replace both together.
- **The gateway never ships a `config.json`.** It is the device's own settings; the test
  asserts the package carries none.

- **`CompressionStream('gzip')` is not reproducible across engines.** Chrome and Node configure
  zlib differently, so the same tar produces different `.fw` bytes. When comparing a
  browser-built package against a Node-built one, compare the **uncompressed tar** digest. A
  fixed mtime in `fw.js` makes the tar layer reproducible; nothing makes the gzip layer so.
- **ustar name fields are 100 bytes** and `tarHeader` throws rather than truncating. Any new
  payload path must stay short.
- **The installer must restart `BirdDogRunner`.** The vendor's `birddog-update-wrapper` stops it
  before calling `./update` and only ever restarts it by rebooting. An installer that exits
  without doing one or the other leaves the device with a dark HDMI output, looking bricked.
- **The camera payload is not offered by this web tool.** `installer/update` still carries a
  `WITH_CAM` block from upstream; it no-ops because the flag defaults to 0 *and* the block
  requires the directory to exist. The test asserts both guards — if you add the camera option,
  those assertions are what to update.
- **The KVM agent installs to `/userdata/bd-kvm`, not `/userdata/birddog-kvm`.** The vendor's own
  KVM hooks are a 1.0.34 feature, absent on 1.0.30, and the vendor updater does
  `rm -rf /userdata/birddog-kvm` on every update. The package *carries* the payload at
  `userdata/birddog-kvm/` — only the install destination differs. This looks like a bug twice.
- **`pkgs.tailscale.com` serves no `Access-Control-Allow-Origin`.** That is the entire reason a
  Worker exists. Keep the proxy narrow: hardcoded host, strict version pattern, two routes.
- **`scripts/sync-from-re.sh` copies `agent/go.mod` and `go.sum` from birddog-re, and Dependabot
  bumps them HERE.** Until upstream `tools/bdkvm/go.mod` carries the same versions, every sync
  silently downgrades them (it did on 2026-09-15, purego 0.11 → 0.10.2, until upstream was
  aligned in birddog-re 191311f). After any Dependabot merge touching `agent/`, apply the same
  bump upstream before the next sync — and note that a bump alone does not rebuild
  `agent/dist/bdkvm-linux-arm64`; that binary is the one proven on hardware, so a rebuild wants a
  device test.
- **`readModule` strips one wrapping directory** (`tar czf x.tgz mymodule/`) but refuses two.
  A module whose `module.conf` is not at the root or one level down is not a layout to support;
  it is an archive of the wrong thing.

## 6. Verifying a change to the archive writer

Do not trust the page's own reader to validate its own writer. The checks worth repeating:

```bash
scripts/build-assets.sh && node test/build-package.mjs
tar tzvf test/out/BirdDog_PLAY-custom-citest.fw          # real tar must agree
python3 -c "import tarfile; tarfile.open('test/out/BirdDog_PLAY-custom-citest.fw').getmembers()"
```

Then extract and `cmp` the members against `installer/` — the test does this for `update`, and
it is the check that catches a subtly wrong header far better than a size comparison.

## 7. The line this project does not cross

The research this is built on recovered a static AES key that BirdDog uses across their whole
product line. **That key is not here, is not needed here, and must never be added here.** The
package format requires no decryption, which is precisely why this tool can be public while the
research repo is not.

Practically: no feature that reads, decrypts or repacks a vendor `.fw`. The test asserts that a
generated package contains no reference to the vendor payload; treat that assertion as a policy
check, not a formality.
